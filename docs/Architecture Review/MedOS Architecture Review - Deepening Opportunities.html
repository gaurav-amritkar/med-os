MedOS Architecture Review: Deepening Opportunities

Identifying shallow modules and opportunities for depth per codebase-design principles

Candidate 1: TenantKeyHolder Depth Enhancement

backend/src/main/java/com/medos/security/TenantKeyHolder.java
Problem: TenantKeyHolder is a shallow module with an interface nearly as complex as its implementation. It mixes concerns of DEK resolution, blind-index key management, caching, rotation logic, and static accessor patterns. Understanding requires bouncing between DekResolver, TenantKeyStore, and cache management.
Solution: Extract DekResolver interface into a separate module, moving cache and rotation logic into dedicated adapters. TenantKeyHolder becomes a thin orchestrator over DEKResolver and BlindIndexKeyResolver, focusing only on tenant isolation and static accessor coordination.
Benefits:
  • Leverage: Callers get DEK resolution through a simple DekResolver interface instead of complex TenantKeyHolder
  • Locality: Cache invalidation and rotation logic concentrate in dedicated modules
  • Testability: DekResolver can be mocked without dealing with TenantKeyHolder's static state and caching complexity
  • Deletion test: Removing the deepened DekResolver would push cache/rotation logic back to callers, increasing complexity

Candidate 2: EncryptionUtil Interface Deepening

backend/src/main/java/com/medos/util/EncryptionUtil.java
Problem: EncryptionUtil is a shallow AttributeConverter that delegates all complexity to PiiCiphertextFormat while managing static initialization and tenant-aware vs single-key resolver switching. The interface (convertToDatabaseColumn/convertToEntityAttribute) is simple but delegates to a complex format object with multiple resolver strategies.
Solution: Extract PiiCiphertextFormat initialization and resolver selection into a separate EncryptionFormatFactory. EncryptionUtil becomes a pure delegate to the factory-produced format, removing static state management and initialization logic from the converter interface.
Benefits:
  • Leverage: Hibernate/JPA gets a simple converter; complexity moved to factory
  • Locality: Encryption key initialization and resolver strategy centralized
  • Testability: Factory can be mocked to return test formats without touching static state
  • Deletion test: Removing factory would force EncryptionUtil to manage initialization and resolver logic directly

Candidate 3: KeyRewrapService Orchestration Refinement

backend/src/main/java/com/medos/security/KeyRewrapService.java
Problem: KeyRewrapService mixes orchestration logic (dry-run planning, failure handling, rotation execution) with direct key store operations. While it already delegates to TenantKeyStore, the Plan and Result records are tightly coupled to the service interface, making it hard to test rotation logic without dealing with entity persistence.
Solution: Extract rotation planning and execution logic into a pure KeyRotationEngine interface. KeyRewrapService becomes a transactional orchestrator that converts between domain entities (KeyRotation) and engine operations, focusing only on persistence and transaction boundaries.
Benefits:
  • Leverage: Callers get rotation logic through a simple engine interface
  • Locality: Rotation algorithm (unwrap/re-wrap/set version) concentrates in engine
  • Testability: Engine can be tested with mock TenantKeyStore without Spring or persistence
  • Deletion test: Removing engine would push rotation logic into service methods, increasing complexity

Candidate 4: BlindIndexKeyService Cache Deepening

backend/src/main/java/com/medos/security/BlindIndexKeyService.java
Problem: BlindIndexKeyService mixes caching logic with key retrieval and rotation operations. The cache is implemented as a ConcurrentHashMap with manual Entry wrapping, mixed with key validation and KEK rotation handling. Understanding requires tracking cache hits/misses alongside key operations.
Solution: Extract cache management into a separate CacheLayer interface with get/put/evict operations. BlindIndexKeyService focuses solely on key retrieval/unwrapping/wrapping and rotation coordination, delegating caching concerns.
Benefits:
  • Leverage: Callers get blind-index keys through a simple service interface; caching details hidden
  • Locality: Cache invalidation, TTL management, and seeding logic concentrated
  • Testability: Cache layer can be mocked to test service behavior under cache hit/miss scenarios
  • Deletion test: Removing cache layer would force service to manage ConcurrentHashMap directly

Top Recommendation

TenantKeyHolder depth enhancement is the strongest candidate because:

  • It addresses the core tenant isolation concern - a cross-cutting concern affecting all PII operations
  • The deletion test clearly shows complexity would push to callers (every service needing tenant DEKs)
  • It enables true testability of PII encryption logic without Spring context or static state
  • It aligns with existing patterns seen in TenantKeyStore (already has real + fake adapters)
  • It reduces coupling between encryption utilities, key services, and tenant context

Addressing this first would provide immediate leverage for testing and maintaining the PII encryption system.
