### Issue #1: Fix Invoice/Payment Number Race Condition

**Priority:** P0 - Critical  
**Area:** Billing / Data Integrity  
**Estimated Effort:** 4 hours

#### Problem
Invoice and payment numbers are generated using `System.currentTimeMillis() % 1000000`, which can produce duplicates under concurrent load.

```java
// Current (BillingService.java:167)
private String generateInvoiceNumber() {
    return "INV-" + System.currentTimeMillis() % 1000000;
}
```

#### Acceptance Criteria
- [ ] Invoice numbers are unique across all time (not just modulo 1,000,000)
- [ ] Payment numbers are unique across all time
- [ ] No unique constraint violations under concurrent load (tested with 100 concurrent requests)
- [ ] Numbers are sequential and human-readable (e.g., INV-000001, INV-000002)
- [ ] Solution survives application restart without gaps or duplicates

#### Technical Approach
1. Create a `database_sequences` table or use PostgreSQL sequences
2. Implement atomic number generation with retry logic
3. Add database unique constraint on `invoice_number` and `payment_number`
4. Write integration test with 100 concurrent threads

#### Files to Modify
- `backend/src/main/java/com/medos/service/BillingService.java`
- `backend/src/main/resources/db/migration/V8__invoice_payment_sequences.sql`

### Issue #2: Fix UHID Generation Race Condition

**Priority:** P0 - Critical  
**Area:** Patient Management / Data Integrity  
**Estimated Effort:** 4 hours

#### Problem
UHID is generated by querying the max existing UHID and incrementing, which fails under concurrent patient registration.

```java
// Current (PatientService.java:103)
private String generateUhid() {
    Integer max = patientRepository.findMaxUhidSequence().orElse(0);
    return String.format("UHID%06d", (max == null ? 0 : max) + 1);
}
```

#### Acceptance Criteria
- [ ] UHIDs are unique across all time
- [ ] No unique constraint violations under concurrent load (tested with 100 concurrent requests)
- [ ] UHIDs are sequential (UHID000001, UHID000002, etc.)
- [ ] Solution survives application restart without gaps or duplicates

#### Technical Approach
1. Create a PostgreSQL sequence `uhid_sequence`
2. Use `nextval('uhid_sequence')` in the insert query
3. Alternatively, use `SELECT ... FOR UPDATE` on a counter row
4. Write integration test with 100 concurrent threads

#### Files to Modify
- `backend/src/main/java/com/medos/service/PatientService.java`
- `backend/src/main/resources/db/migration/V8__uhid_sequence.sql`

### Issue #3: Standardize Patient Balance Calculation

**Priority:** P0 - Critical  
**Area:** Billing / Data Integrity  
**Estimated Effort:** 6 hours

#### Problem
Two different services calculate `patient.outstanding` differently:
- `BillingService.syncPatientBalance()`: sums `billed + paid` charges
- `PharmacyService.syncPatientBalance()`: sums only `unbilled` charges

This causes the balance to jump unpredictably after pharmacy dispenses or billing operations.

#### Acceptance Criteria
- [ ] Single source of truth for balance calculation
- [ ] Formula: `outstanding = SUM(charges WHERE status IN (billed, paid)) - SUM(payments WHERE status = success)`
- [ ] Balance is updated atomically with every charge/payment operation
- [ ] No N+1 queries in balance sync
- [ ] All existing tests pass
- [ ] Add integration test verifying balance after: admission, pharmacy dispense, invoice generation, payment

#### Technical Approach
1. Create a single `PatientBalanceService` with one `recalculateBalance(UUID patientId)` method
2. Update `BillingService`, `PharmacyService`, and `AdmissionService` to call this service
3. Remove duplicate `syncPatientBalance()` methods
4. Add database trigger or application event to recalculate on charge/payment changes

#### Files to Modify
- `backend/src/main/java/com/medos/service/BillingService.java`
- `backend/src/main/java/com/medos/service/PharmacyService.java`
- `backend/src/main/java/com/medos/service/AdmissionService.java`
- `backend/src/main/java/com/medos/service/PatientBalanceService.java` (new)

### Issue #4: Add RBAC on Billing and Encounter Endpoints

**Priority:** P0 - Critical  
**Area:** Security / Authorization  
**Estimated Effort:** 8 hours

#### Problem
Sensitive endpoints allow any authenticated user to access any patient's data:
- `GET /api/billing/patients/{id}/invoices` — any user can view any patient's invoices
- `GET /api/billing/patients/{id}/unbilled` — any user can view any patient's unbilled charges
- `GET /api/encounters/{id}` — any user can view any doctor's clinical notes

#### Acceptance Criteria
- [ ] Billing endpoints require `BILLING` or `ADMIN` role
- [ ] Encounter endpoints require the requesting user to be the patient's assigned doctor, or `ADMIN`
- [ ] Receptionist can view patient demographics but not clinical notes or billing details
- [ ] Nurse can view encounters for patients in their ward only
- [ ] All authorization checks are logged in audit trail
- [ ] Add RBAC matrix test covering all 6 roles × all endpoints

#### Technical Approach
1. Create custom `@PreAuthorize` expressions:
   - `@PreAuthorize("hasRole('BILLING') or hasRole('ADMIN')")` for billing
   - `@PreAuthorize("isDoctorOfPatient(#id) or hasRole('ADMIN')")` for encounters
2. Implement `isDoctorOfPatient()`, `isNurseOfPatient()` methods in a custom security expression handler
3. Add service-layer authorization checks as defense in depth
4. Update `RbacMatrixTest` to cover these endpoints

#### Files to Modify
- `backend/src/main/java/com/medos/controller/BillingController.java`
- `backend/src/main/java/com/medos/controller/EncounterController.java`
- `backend/src/main/java/com/medos/config/SecurityConfig.java`
- `backend/src/test/java/com/medos/security/RbacMatrixTest.java`
